# C04 agenda identity and decision retention

C04 uses the existing `phase3_collection_items` table and C02 canonical transaction lock; it adds no schema migration. The following keyed collections are additive: `agenda_document_aliases`, `agenda_document_revisions`, `agenda_document_observations`, `agenda_unresolved_documents`, `agenda_observations`, `agenda_candidate_revisions`, `agenda_identity_resolutions`, and `agenda_decision_events`. Existing `source_documents`, `agenda_staged_records`, published rows, versions, and IDs remain in place.

A logical document ID is independent of its PDF hash. A source URL plus reliable full meeting date is an alias; another URL or changed date with a possible existing match is quarantined. The reviewer-only `GET /api/reviewer/agenda-documents/unresolved` and `POST /api/reviewer/agenda-documents/{id}/resolve` endpoints explicitly link to an existing document or create a separate document ID. The request requires the unresolved observation revision and a reason. It records actor/reason under the canonical lock, then returns `retry_required`; a later verified source run activates the aliased PDF. A stale or conflicting resolution is 409.

The current parser has no authoritative agenda item ID. Its ordinal is only an observation key within one immutable document/extraction revision. First-seen candidates get stable internal IDs; an exact legacy staged ID can be retained when unambiguous. On a changed PDF, unmatched items enter `identity_unresolved` and leave prior decisions and published snapshots untouched. The reviewer-only `GET /api/reviewer/agenda-observations/unresolved` and `POST /api/reviewer/agenda-observations/{id}/resolve` endpoints link the occurrence to an existing candidate or deliberately create a new one, with expected observation/candidate revisions, actor/reason, and a durable audit event. Linking changed content creates a pending content revision. An unchanged replay leaves state revision, notes, actor, decision time, first discovery date, geometry, and publication intact.

Any unresolved document or candidate makes agenda health `degraded` with `agenda_identity_unresolved` and a count. It is never reported as a complete healthy refresh merely because the PDF/text copies were verified.

Agenda review actions carry `expected_revision`; they lock and compare before mutating. A stale action returns `review_revision_conflict` (409). Decision events retain previous status, actor, notes, time, content revision and state revision. Old agenda rows without explicit revision metadata are adopted on exact replay; an existing approved/rejected decision receives a marked legacy baseline event with unknown actor/time if that information was never stored. Existing published IDs are preserved. A rejected new revision does not retract an older public record.

If an agenda candidate already has a public record, an approval returns that **persisted** snapshot only when its public-content fingerprint is unchanged. A materially changed revision returns `agenda_publication_update_pending` (409) and stays pending, preserving the old public version. C06 must implement the versioned public update and event before that path may approve changed public content; C04 must not present a constructed but unstored snapshot as live.

O01 uploads and verifies the exact PDF and extracted-text pair before C04 obtains the canonical lock. C04 then checks the sealed required reference set, the text-to-PDF parent, and both checksums inside the same transaction as item-level merge. Upload/parse failure leaves old state active and retryable; no object-store network I/O occurs under the lock. Archive-page evidence is separate from the required PDF/text pair. Discovery covers only the configured recent-document window; curated fallback reports degraded health, not complete archive coverage.

Unlocated agenda records stage with `geometry=null` and `location_required=true`. Approval is blocked until supported geometry exists. Existing historical records exactly at Huntsville's center are **not** automatically deleted or altered: some may be legitimate and need provenance-based audit. Reviewer geometry correction remains U04's fuller workflow.

For rollout, back up the database and reconcile existing agenda IDs, published IDs, decision exports, and counts on a copied database. First exact replay lazily attaches aliases and baseline revisions without replacing decisions. Do not infer identity from a title, source phase, or page order. Inspect unresolved observations and explicitly resolve them before considering coverage current. Do not downgrade or delete additive revision collections after new decisions; rollback the application code and stop agenda writes while serving the last known published snapshot, then repair and replay verified source observations. Retain O01 object storage and its manifest with the database backup.

Before rollout, run `python -m app.ingestion.agenda_inventory` inside the configured API environment against a copied database. It performs read-only collection reads and reports counts plus bounded ID samples of documents lacking a URL/date alias or revision, candidates lacking a revision, and reviewed candidates lacking a decision event. Existing rows remain visible even if they are not within the recent-document fetch window. The inventory does not assign an ID, infer a match, or repair data. Preserve its JSON output with the rollout evidence.

**[C10 guarded historical backfill](../implementation/2026-09-readiness/C10-guarded-agenda-history-backfill.md) is required before release** if that inventory reports gaps that an exact verified replay cannot cover. This separate planned guide was formerly called C04b. C10 must use an operator-reviewed mapping of legacy document/candidate/public IDs to authoritative source evidence, record actor/reason and the input database/export checksums, create immutable alias/revision/baseline rows under the canonical lock with expected-revision checks, and offer a no-write dry run plus an idempotent apply on a database copy. It must refuse ambiguous title/ordinal matches and preserve every existing decision, note, and public snapshot. C04 itself intentionally leaves unmatched legacy rows unchanged; no automatic historical mutation is included in this PR. A recorded zero-gap inventory satisfies this conditional requirement without a backfill.
